# 评测边界与扩展计划

## 固定原则

使用 mock 歌曲和 POI，真实 Jev 推理。人工标准答案是独立依据，不以 Jev 自己的输出作标准。
候选字段应来自拟接入接口的实际结构，未来按真实结构修订样本。
mock 固定候选可以评测筛选与排序，不能证明真实搜索接口的召回能力。
距离、营业时间、数量、ID 去重由 Python 处理；Jev 判断语义，未知字段不补造。

## 数据规范

每行一个 Case：id、domain、task、split、state、question、gold、rationale、tags。
question 按官方 SDK 类型定义；Choice gold 是选项 key；Noul gold 是 bool 或 null；
Score gold 是从 0 开始的量表整数，真实 score 是概率加权的期望值，可以为小数。
Score 排序样本增加 ranking_group 和 candidate_id。同组必须使用同一量表、split，候选 ID 唯一。
同一个 task 的 Choice 选项和 Score 量表应保持一致，语义不同的任务使用不同 task 名称。
标准答案和解释不放在 state 中；候选不得携带 gold、relevance 等标签字段。

## 正式数据集目标（尚未完成）

2 领域 × 3 能力 × 60 条独立样本，另加 60 条组合链路样本。
来源、实体或改写模板族整体划分 dev / calibration / test，避免同源样本泄漏。
每条样本保留标注依据；导航固定位置和时间；开放场景音乐匹配必须提供可判断的元数据。
覆盖否定、改口、多轮指代、缺失信息、无相关候选、同名不同实体、版本冲突、选项乱序和干扰文本。
测试集冻结后不得用来调阈值和问题描述。初始 smoke 不作为正式测试集。

## 后续实验

1. 意图、约束理解、多轮消歧、筛选排序、结果可用性。
2. Noul 单候选匹配概率排序 vs Score 量表排序，同候选比较。
3. Choice 选项和候选随机置换，测一致率和位置敏感性。
4. 单问 vs 同 state 多问的质量、延迟和用量；依赖前一步的判断分阶段。
5. Choice → Noul → Score 的组合链路，汇总请求级成功率、硬条件违反率。
6. 置信度门控的覆盖率 / 错误率曲线；confidence 不等于正确概率。
7. 规则、现有模型录制结果作为外部基线，未提供录制结果前不虚构比较。
8. 对请求级统计作 bootstrap 置信区间，候选对不能当独立请求。

当前基础项目未实现上述全部实验，优先把可靠的原始记录和三种能力指标跑通。
